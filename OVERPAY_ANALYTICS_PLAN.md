# Overpay analytics

Use Rolimon’s [`#value-requests`](https://discord.com/channels/415246288779608064/535250426061258753) as the first live source. Use RoPost’s Proof Checker to cross-check the pilot sample. The alt can already open the channel in Edge. An initial read found proof images, moderation notices, compact `S:` / `R:` / `D:` labels, and both month-first and day-first dates. Automated reads and historical pricing coverage still need verification.

## 1. Collect a live sample on demand

- Build a local, read-only collector that opens the channel in a dedicated persistent Edge profile. The user signs in to their alt in that profile once. Before collecting, verify the expected account and channel. If Discord prompts for sign-in, stop and explain how to resume. Keep the profile and collected data outside the repository and keep authentication in the browser.
- Start with an on-demand command. Each run catches up from the last recorded Discord message and rereads a small overlap for edits. Save the original message ID and link, Discord post and edit timestamps, message text, and evidence images in local storage. Store the message ID and attachment IDs alongside the images. Advance the checkpoint only after the batch is saved. A retry should update the same records without skipping or duplicating posts.
- Read 50–100 recent live messages, then run the collector again with the same profile. Check session reuse, catch-up, and deduplication. Inspect proof coverage for one liquid, one mid-volume, and one rare item. Summarize moderation posts, posts with usable trade data, duplicate trades, completed proofs, isolated targets, eligible submitted totals, and coverage for historical cross-checks.
- Add an optional Windows schedule once catch-up works. The next run can read posts that are still in the channel after the PC has been off. Consider a private hosted VM later if collection needs to run while the PC is off.

## 2. Parse proof posts and confirm both trade sides

```text
Item(s): <name or acronym>
Values: <side A> vs <side B>
Sender: <Roblox username>
Receiver: <Roblox username>
Date: <trade date>

<trade screenshot>
```

- Use the post text first. Accept short labels, `v` and `vs`, `k` and `m` amounts, quantities, and omitted fields. Keep raw text alongside normalized fields. Resolve names and acronyms to typed Roblox IDs. Flag missing units and ambiguous dates for review. Use the screenshot or other dates in the same proof when they resolve the ambiguity. Store the trade date separately from the Discord post timestamp.
- Read both screenshot baskets, including small adds, quantities, and any visible Robux. Use OCR or image extraction where the text leaves these unclear. Verify that the evidence shows a completed trade before including it in the primary sample. Record any demonstrated staff review separately from the submission and completion status.
- Deduplicate by an actual trade ID when present. Otherwise match reposts using the trade date, participants, both normalized item baskets, and any visible Robux or copy IDs. Use matching evidence images to help identify reposts. Keep uncertain matches for review and retain the original source links for merged records.
- Keep the supplied formatting examples as regression cases. Ice Valkyrie with Perfectly Legitimate has **+13k** on the submitted totals, with 330k opposite the 317k basket. It is evidence for a bundled target. Fuchsia Fantastique is isolated and shows **+5k**, with 155k opposite 150k. Scissors is explicitly named because its 100k value exceeds half of Fuchsia Fantastique’s 150k value. Use the target’s position in the screenshot to orient the calculation in both examples.

## 3. Aggregate submitted OP and cross-check historical values

- Use the two submitted totals for the primary benchmark. Include unique completed trades where one copy of the target is alone on its side, the screenshot confirms an item-only exchange, and both submitted totals can be matched to the correct sides. Flag missing or ambiguous totals for review. Preserve both submitted totals and calculate signed OP as **submitted opposing total − submitted target total**. Keep one-for-one swaps separate from one-for-many benchmarks. In a one-for-many trade, acquiring the single item is the upgrade perspective and giving it up is the downgrade perspective. Count the trade once for the target item. Inspect proofs with visible Robux during the pilot to establish how their amounts and fees are represented.
- When both baskets have complete history, recalculate OP using Rolimon’s assigned values in effect at the time of the trade and record the difference from submitted OP. Record the value source and effective timestamp for each item. If a date-only proof falls on a day with a relevant value change, resolve the timestamp from the evidence or mark the historical cross-check unavailable. Report historical coverage alongside the cross-check results. Proofs that meet the primary criteria qualify even when historical pricing is incomplete. [Example Rolimon’s value history](https://www.rolimons.com/item-value-changes/19027209)
- Show median OP, mean OP, the middle 50% range, sample count, date window, last successful collection, and links to the source posts. Start by evaluating a 30-day window with a provisional minimum of 10 unique eligible trades per item and trade shape. Show the sample count for thinner groups and require sufficient coverage in both windows before showing a trend. Use pilot counts to revise these display thresholds.
- Label the primary result **Based on submitted values** and explain that voluntary submissions can overrepresent unusually high overpays. Keep historical cross-check values out of the submitted aggregates. If RoUtility is tested later, compare results across imbalance cutoffs and report how many trades each cutoff removes. Give inferred OP its own benchmark and sample count.

## 5. Serve Marketplace estimates within 10 seconds

The Marketplace widget now uses seven days of RoUtility snapshots. The architectures below describe options for serving a separate estimate backed by Rolimon’s historical valuations. [Current Marketplace calculator](README.md#item-overpay)

The previous cold-cache scheduler acquired profiles on page load. The observed samples needed 172 distinct profiles for SKOTN and 173 for CF to price every eligible trade if all historical evidence existed. At one new profile every 2.5 seconds, each item alone would need over seven minutes to fetch that many profiles, even before provider cooldowns. The live test received a roughly 46-minute cooldown. [Cold-cache results](tools/overpay/README.md#historical-marketplace-cold-cache-verification)

| Architecture | Feasibility and serving latency | Cost | Maintenance and accuracy |
| --- | --- | --- | --- |
| Shared historical database with scheduled backfill | Practical with existing sources for a prioritized catalog. Ingest RoUtility history and hydrate needed profiles ahead of demand. One cached API request runs a batch time-range join for assets already ingested. A cache miss that needs upstream profiles can still miss the target. | Managed database, ingestion compute, storage, backups, and API requests. Deduplication across items and users saves upstream requests. | Maintain durable jobs, rate limits, provenance, and parser monitoring. Can preserve current price rules exactly. Bootstrap takes time, and retries, provider gaps, and catalog breadth govern coverage. |
| Bulk historical acquisition | Seek one-time historical exports and incremental updates from Rolimon's and RoUtility. Use a validated complete starting snapshot and replay timestamped changes. This replaces many per-item fetches when a feed is available. The existing current item feed and public recent Value changes page are candidates for collecting forward. Their presence does not establish complete historical delivery, and Value events alone leave gaps for dated RAP. | Low request volume when data arrives in bulk. Provider access or export costs are unknown. Imports, retained revisions, and reconciliation add storage and job costs. | Highest potential breadth with a dependable feed. Validate pagination, sequence or time watermarks, late corrections, and RAP timestamps. A gap in the feed must stop certification through that interval. [Rolimon's recent Value changes](https://www.rolimons.com/valuechanges) |
| Precompute per-item OP and publish versioned results to a CDN | Removes all upstream calls from Marketplace page load for published items. A single item document can carry both groups, coverage, confidence, observation window, and refresh time. Feasible using the shared database as input. | Object storage, write/read operations, and scheduled compute. There is no database query charge per view on a cache hit. Cost grows with refreshed items and payload sizes as well as traffic. [Example object storage pricing](https://developers.cloudflare.com/r2/pricing/) | Recompute on trade revisions, price corrections, and observations aging out of the 30-day window. Publish both groups and their metadata together. Match the existing resolver over the same input revisions. Freshness depends on ingestion and publication cadence. [PostgreSQL materialized views](https://www.postgresql.org/docs/18/rules-materializedviews.html) |
| Bundled summaries and periodic extension downloads | Can serve an installed snapshot on a slow connection and handles popular items well. A complete long-tail catalog increases download size. A fresh install still depends on its bundled snapshot or a successful download. | Lowest serving complexity. Larger bundles or frequent catalog-wide downloads shift cost to release size and bandwidth. | Validate version compatibility and report data age. Estimates get stale between refreshes, so this is a fallback for the last good snapshot. |

Start with a shared database and precomputed CDN delivery for tracked items. Prioritize SKOTN, CF, and their counterpart profiles. Add provider exports and deltas if available to improve long-tail coverage. Keep ingestion off the page-load path. A cache miss should return quickly with its last verified estimate and timestamp, or an explicit insufficient-data state, while the ingestion job fills gaps. Measure successful estimate coverage separately so a fast insufficient-data response cannot satisfy the latency goal.

Store raw source revisions and normalized Value intervals, timestamped RAP observations, and trade observation windows. Join every copy against its full observation window. Only use same-day RAP when the evidence establishes no assigned Value. Preserve overlaps, missing periods, late revisions, and source timestamps for audit. Continue applying the existing eligibility and imbalance rules and publishing both raw and market-rate statistics. A live trade feed arriving late and a historical price gap are distinct states.

For acceptance, measure cold-extension p95 from navigation to a usable estimate on desktop and mobile, targeting 10 seconds across the tracked catalog. Set a freshness target for trade ingestion and aggregate publication, and report age separately from latency. Track 80% and 95% pricing coverage per item and trade group, standard-confidence rate, percentage of requests with a usable estimate, and parity with the existing historical resolver on reviewed fixtures. Under provider cooldown, demonstrate fast delivery of the last verified snapshot with its age visible. As an illustrative cost model, 1,000 items refreshed hourly generate up to 720,000 writes per 30-day month. At 20 KB per item, the latest snapshots total about 20 MB. With one million uncached object reads, this example fits within the published R2 Standard monthly free allowances for the serving layer. Version retention, the valuation database, ingestion, and any provider charges are additional. [Example object storage pricing](https://developers.cloudflare.com/r2/pricing/)
